## ۱. تصویر کلی

### سایت قبلی فقط فایل بود

سایت اینوتک یک مشت فایل آماده است. مثل بروشور چاپ‌شده: هرکسی بازش می‌کند همان
چیزی را می‌بیند که از قبل چاپ شده. نه کسی را می‌شناسد، نه چیزی یادش می‌ماند.

### INLEARN باید چیزهایی یادش بماند

- این آدم ثبت‌نام کرده، رمزش این است
- این آدم فلان دوره را خریده، پس اجازه دارد ببیندش
- قیمت این دوره چقدر است
- این سفارش پرداخت شده یا نه

بروشور هیچ‌کدام را نمی‌تواند. پس چیزی لازم است که بنشیند یک گوشه، همه را نگه دارد،
و هر وقت سایت پرسید جواب بدهد. **آن چیز بک‌اند است.**

### چرا استرپی و نه نوشتن از صفر

استرپی اینها را **آماده** می‌دهد:

- جدول کاربران با رمز هش‌شده
- ثبت‌نام، ورود، خروج
- فراموشی رمز با ایمیل
- ورود با گوگل/اپل/لینکدین
- نقش و سطح دسترسی
- پنل مدیریت برای CEO که بدون کد محصول اضافه کند

اگر اینها را خودت بنویسی، ماه‌ها طول می‌کشد و **احتمال زیاد جایی‌اش امن نخواهد بود**.
احراز هویت یکی از آن چیزهایی است که نباید از صفر نوشت — نه چون سخت است، چون
راه‌های شکستنش آن‌قدر زیادند که تنهایی همه‌شان را نمی‌بینی.

### مرزبندی با وردپرس

وردپرس در پروژه هست، ولی برای کار خودش:

| | چه چیزی توش است | کی مدیریتش می‌کند |
|---|---|---|
| **وردپرس** | مقاله‌ها و بلاگ سایت اصلی | سئوکار |
| **استرپی** | همه‌چیز INLEARN: دوره، قیمت، ویدیو، کاربر، سفارش | CEO |

دو سیستم، دو کار جدا، بدون همپوشانی. اگر محصولات در وردپرس و سفارش‌ها در استرپی
بودند، هر بار باید یکی از دیگری می‌پرسید «محصول شماره ۷ چیست؟» — و اگر وردپرس آن را
پاک می‌کرد، سفارش‌ها به هوا اشاره می‌کردند. این کلاسیک‌ترین اشتباه معماری است.

## ۲. چرا JWT

این مهم‌ترین تصمیم فنی این بخش بود. بذار گزینه‌ها را کنار هم بگذارم.

### مسئله چیست

بعد از اینکه کاربر یک بار لاگین کرد، **هر درخواست بعدی** باید ثابت کند که همان آدم
است. وگرنه هر کسی می‌تواند بگوید «من بردیا هستم، دوره‌هایش را بده».

راه‌های رایج:

### گزینه ۱ — نشست سمت سرور (session)

سرور یک جدول نگه می‌دارد: «شناسه‌ی ABC یعنی کاربر شماره ۵». مرورگر آن شناسه را در
کوکی نگه می‌دارد و هر بار می‌فرستد.

**چرا برای ما مناسب نبود:**

سایت ما روی GitHub Pages است و استرپی روی دامنه‌ی دیگری. کوکی‌ها ذاتاً به دامنه
گره خورده‌اند، و کوکیِ بین دو دامنه (third-party cookie) امروز در بیشتر مرورگرها
یا بلاک می‌شود یا محدودیت‌های سنگین دارد. یعنی زیرساختی که باید ساده باشد، تبدیل
می‌شود به منبع دائمی باگ‌هایی که فقط روی بعضی مرورگرها اتفاق می‌افتند.

### گزینه ۲ — توکن API

استرپی چیزی به اسم API Token دارد که در Settings می‌سازی.

**چرا نه:**

| | JWT | API Token |
|---|---|---|
| نماینده‌ی کیست | یک **کاربر** | یک **برنامه** |
| از کجا می‌آید | جواب لاگین | خودت دستی می‌سازی |
| دسترسی | فقط مال همان کاربر | معمولاً گسترده |
| کجا باید باشد | مرورگر کاربر | فایل تنظیمات سرور |

API Token مال وقتی است که یک **برنامه** — مثلاً اسکریپت بیلد ما که لیست دوره‌ها را
می‌خواند — نیاز به دسترسی دارد. کاربر در کار نیست.

> ⚠️ **API Token هیچ‌وقت نباید در کد سایت باشد.** هرچه در کد React بنویسی، مرورگر
> دانلودش می‌کند و هر کسی می‌تواند بخواندش. اگر JWT یک کاربر دزدیده شود، فقط حساب
> خودش لو می‌رود. اگر API Token لو برود، همه‌چیز.

### گزینه ۳ — خودمان رمز را چک کنیم

یعنی رمز را در دیتابیس بگذاریم و موقع ورود مقایسه کنیم.

**چرا نه:** حتی این جمله‌ی ساده ده‌ها تله دارد — رمز باید هش شود (با bcrypt، نه
MD5)، مقایسه باید مقاوم به حمله‌ی زمانی باشد، باید محدودیت تعداد تلاش بگذاری،
جریان بازیابی رمز باید امن باشد، و... استرپی همه‌ی اینها را حل کرده.

### گزینه ۴ — سرویس بیرونی (Auth0، Firebase)

گزینه‌ی بدی نیست. ولی یک فروشنده‌ی دیگر، یک هزینه‌ی دیگر، و یک جای دیگر که داده‌ی
کاربرانت آنجاست. **ما استرپی را به‌هرحال داریم و این را مجانی می‌دهد.**

### تصمیم: JWT

**JWT یک رشته است که سرور امضایش کرده.** داخلش می‌نویسد «این کاربر شماره ۵ است» و
با کلید مخفی خودش مهر می‌زند. مرورگر آن را نگه می‌دارد و هر بار در هدر می‌فرستد.

چرا خوب است:
- کوکی نیست، پس مشکل دامنه ندارد
- سرور لازم نیست چیزی یادش بماند؛ امضا را چک می‌کند و تمام
- اگر کسی دستکاری‌اش کند، امضا نمی‌خواند و رد می‌شود

### ولی استرپی ۵ یک حالت دوتوکنی دارد

این را وسط کار کشف کردیم. توکن را باز کردیم:

```json
{ "userId": "1", "sessionId": "5fcd...", "type": "access",
  "iat": 1789301347, "exp": 1789301947 }

عمر: ۶۰۰ ثانیه = ۱۰ دقیقه
```

علتش این خط در `inlearn-api/config/plugins.js` است:

```js
'users-permissions': {
  config: {
    jwtManagement: 'refresh',
    sessions: { httpOnly: true },
  },
},
```

یعنی:

| توکن | عمر | کجاست |
|---|---|---|
| `access` | ۱۰ دقیقه | در جواب، جاوااسکریپت نگهش می‌دارد |
| `refresh` | ۱۴ روز | **کوکی httpOnly** |

تأییدش کردیم:

```
Set-Cookie: strapi_up_refresh=...; path=/; samesite=lax; httponly
```

**چرا این طراحی بهتر است؟** اگر توکن اصلی دزدیده شود، فقط ۱۰ دقیقه ارزش دارد. و آن
توکن بلندمدت در کوکی `httpOnly` است — یعنی **جاوااسکریپت اصلاً نمی‌تواند بخواندش**،
پس حتی اگر کد مخربی در صفحه اجرا شود، دستش به آن نمی‌رسد.

بهترین هر دو دنیا: سرعت و سادگی JWT، به‌علاوه‌ی امنیت کوکی httpOnly برای بخش
حساس.

## ۳. کارهایی که در پنل استرپی کردیم

### ۳.۱ نصب

```bash
cd "/d/Bardia/FARA Projects/InnoTech and api"
npx create-strapi-app@latest inlearn-api
```

جواب‌ها و **چرا**:

| سؤال | جواب | چرا |
|---|---|---|
| Login/Sign up | **Skip** | Strapi Cloud میزبانی پولی خودشان است؛ ما سرور جدا داریم |
| database | **SQLite** | کل دیتابیس یک فایل است، هیچ نصبی نمی‌خواهد. روی سرور واقعی Postgres |
| example structure? | **No** | وگرنه پنل پر می‌شود از جدول‌های الکی و نمی‌فهمی کدام مال توست |
| TypeScript? | **No** | یکی‌یکی. اول بک‌اند را بفهم |
| install dependencies | **Yes** | |
| git repository | **Yes** | (که در عمل نساخت — بخش ۶ را ببین) |

بعد:

```bash
cd inlearn-api && npm run develop
```

**`develop` در برابر `start`:**

| حالت | دستور | ویژگی |
|---|---|---|
| توسعه | `npm run develop` | می‌توانی جدول و فیلد **بسازی** |
| تولید | `npm start` | ساختار **قفل** است، فقط داده وارد می‌شود |

چون ساختن جدول جدید یعنی استرپی واقعاً **فایل کد می‌نویسد**، و روی سرور واقعی
نمی‌خواهی کسی از توی مرورگر ساختار دیتابیس را عوض کند.

### ۳.۲ جدول User را استرپی از قبل دارد

در `Content-Type Builder` می‌بینی:

| فیلد | کارش |
|---|---|
| `username`, `email` | هویت |
| `password` | **هش‌شده** ذخیره می‌شود، نه خام |
| `provider` | با چه چیزی وارد شده: `local` یا `google` |
| `resetPasswordToken` | کد بازیابی رمز |
| `confirmed`, `blocked` | تأیید ایمیل و مسدودسازی |
| `role` | سطح دسترسی |

قفل کنارشان یعنی استرپی خودش مدیریتشان می‌کند.

### ۳.۳ دسترسی‌ها — مهم‌ترین قدم

استرپی به هر درخواست یک سؤال می‌پرسد: **«تو کی هستی؟»**

دو نقش از پیش‌ساخته:

| نقش | یعنی کی |
|---|---|
| **Public** | کسی که **وارد نشده** |
| **Authenticated** | کسی که لاگین کرده |

> ⚠️ **تله‌ی اول: دو بخش «Roles» وجود دارد.**
>
> | مسیر | مال کیست |
> |---|---|
> | `ADMINISTRATION PANEL → Roles` | کسانی که وارد **پنل استرپی** می‌شوند |
> | `USERS & PERMISSIONS PLUGIN → Roles` | کسانی که از **سایت تو** استفاده می‌کنند |
>
> ما دومی را می‌خواهیم. اولی `Author`/`Editor`/`Super Admin` دارد و هیچ ربطی به
> دانشجوها ندارد.

مسیر: **Settings → USERS & PERMISSIONS PLUGIN → Roles → Public → Users-permissions → AUTH**

این پنج تا را روشن کن:

```
✅ register         ثبت‌نام
✅ callback         ورود  ← اسمش گیج‌کننده است
✅ forgotPassword   فرستادن کد بازیابی
✅ resetPassword    ثبت رمز جدید با آن کد
✅ connect          شروع مسیر گوگل/اپل/لینکدین
```

و بقیه خاموش.

#### چرا کسی که ثبت‌نام می‌کند `Public` است

چون در آن لحظه هنوز حساب ندارد. به نظر عجیب می‌آید که به غریبه اجازه بدهی، ولی اگر
ندهی **هیچ‌کس هیچ‌وقت نمی‌تواند حساب بسازد**.

#### چرا `callback` اسمش این است

منطقاً باید `login` باشد. ولی استرپی یک اندپوینت را برای **دو کار** استفاده می‌کند:
ورود با ایمیل و رمز، و بازگشت از گوگل. اسم فنی آن بازگشت **callback** است.

**اگر `callback` را تیک نزنی هیچ‌کس نمی‌تواند وارد شود** — حتی با ایمیل ساده. این
متداول‌ترین جایی است که آدم‌ها گیر می‌کنند، چون دنبال `login` می‌گردند.

#### اصل: فقط چیزی را باز کن که لازم داری

هر تیک یک **در باز** است. مثلاً `sendEmailConfirmation` را عمداً خاموش گذاشتیم:
روی نقش Public است، یعنی هرکسی بدون حساب می‌تواند صدایش بزند. یک اسکریپت ساده
می‌تواند هزار بار بزند و سرور تو هزار ایمیل بفرستد — سهمیه‌ات تمام می‌شود و
دامنه‌ات اسپم علامت می‌خورد. آن‌وقت **ایمیل‌های واقعی بازیابی رمز هم به اسپم
می‌روند**.

اضافه کردن یک تیک ده ثانیه است؛ پیدا کردن یک در بازِ فراموش‌شده، ماه‌ها.

### ۳.۴ CORS

قبل از اینکه فایلی را عوض کنیم، **تست کردیم**:

```bash
curl -i -X OPTIONS "http://localhost:1337/api/auth/local" \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST"
```

جواب:

```
Access-Control-Allow-Origin: http://localhost:5173   ✅
```

**از قبل درست بود.** استرپی در حالت توسعه به همه اجازه می‌دهد.

> **درس:** قبل از عوض کردن تنظیمات، تست کن. نصف وقت مشکلی وجود ندارد.

> ⚠️ روی سرور واقعی این باید **محدود** شود به دامنه‌ی سایت، وگرنه هر سایتی
> می‌تواند به API تو درخواست بزند.

## ۴. کد سمت سایت

همه در `Innotech/src/features/inlearn/`.

### ۴.۱ `services/authService.js` — تنها جایی که با استرپی حرف می‌زند

**چرا یک فایل جدا؟** چون کامپوننت‌ها نباید بدانند استرپی وجود دارد. اگر فردا بک‌اند
عوض شود، فقط این فایل عوض می‌شود و هیچ صفحه‌ای دست نمی‌خورد.

```js
const API_URL = (import.meta.env.VITE_INLEARN_API_URL ?? "").replace(/\/+$/, "");
```

آدرس از متغیر محیطی می‌آید، نه هاردکد. چون روی لپ‌تاپ `localhost:1337` است و روی
سرور چیز دیگری.

**تصمیم مهم: هیچ‌چیز تقلبی نیست.**

```js
if (!API_URL) {
  throw new Error("The INLEARN API is not connected yet.");
}
```

سرویس قبلی فقط یک شیء در localStorage می‌نوشت و می‌گفت «Signed in». برش داشتیم.
یک stub که موفقیت گزارش می‌دهد، **شکل اشتباهی به صفحه یاد می‌دهد و کار باقی‌مانده
را پنهان می‌کند**.

توابعش:

| تابع | اندپوینت استرپی |
|---|---|
| `logIn()` | `POST /api/auth/local` |
| `register()` | `POST /api/auth/local/register` |
| `requestPasswordReset()` | `POST /api/auth/forgot-password` |
| `resetPassword()` | `POST /api/auth/reset-password` |
| `providerSignInUrl()` | ریدایرکت به `/api/connect/:provider` |
| `completeProviderSignIn()` | `GET /api/auth/:provider/callback` |

**نکته‌ی `logIn`:**

```js
const payload = await request("/api/auth/local", {identifier: email, password});
```

استرپی اسمش را `identifier` گذاشته چون هم ایمیل قبول می‌کند هم نام کاربری.

**نکته‌ی خطاها:**

```js
throw new Error(payload?.error?.message || "Something went wrong. Try again.");
```

پیام واقعی استرپی را بیرون می‌دهیم نه کد وضعیت، تا «Invalid identifier or
password» عیناً به فرم برسد.

**نکته‌ی «Keep me signed in»:**

```js
function readStore(remember) {
  return remember ? window.localStorage : window.sessionStorage;
}
```

`localStorage` بعد از بستن مرورگر می‌ماند، `sessionStorage` نمی‌ماند. همین تفاوت،
کل معنای آن چک‌باکس است.

### ۴.۲ چرا ورود با گوگل یک **ریدایرکت** است نه `fetch`

```js
window.location.assign(providerSignInUrl(provider));
```

این را بفهم چون قلب OAuth است:

```
۱. کاربر روی «Log in with Google» می‌زند
۲. مرورگر می‌رود پیش گوگل: «سایت شماره ۱۲۳۴۵ هستم»
۳. گوگل نگاه می‌کند: آها، INLEARN Academy
۴. پنجره‌ی انتخاب حساب ← همان پاپ‌آپی که انتظار داری
۵. کاربر حسابش را می‌زند
۶. گوگل او را برمی‌گرداند، با یک کد یک‌بارمصرف در آدرس
۷. استرپی آن کد را با رمز مخفی‌اش می‌دهد به گوگل   ← سرور به سرور
۸. گوگل می‌گوید: این آدم فلانی است، ایمیلش این است
۹. استرپی کاربر را می‌سازد و JWT خودش را صادر می‌کند
```

**چرا دو مرحله؟** چون هرچه از مرورگر رد شود دیده می‌شود. آن `code` در نوار آدرس
است و هرکسی می‌بیندش — ولی **بدون رمز مخفی بی‌ارزش است**. مثل قبض لباس‌شویی: کسی
قبض را بدزدد، بدون مهر مغازه چیزی تحویلش نمی‌دهند.

مرحله‌ی ۷ حتماً باید سمت استرپی باشد. اگر `client_secret` در کد سایت بود، هرکسی
سورس را باز می‌کرد و می‌توانست خودش را جای سایت تو جا بزند.

**دو تا «کد» در این ماجرا هست و هیچ ربطی به هم ندارند:**

| | مال کی | عمرش | کارش |
|---|---|---|---|
| `code` | گوگل | چند دقیقه، یک‌بار | فقط برای معاوضه |
| `jwt` | **استرپی** | ۱۰ دقیقه | کارت ورود به سایت تو |

از مرحله‌ی ۹ به بعد **گوگل دیگر در ماجرا نیست**. کاربر یک حساب در دیتابیس **تو**
دارد. گوگل فقط یک بار آمد، ضمانت کرد، و رفت.

و توکن بلافاصله از نوار آدرس پاک می‌شود تا رفرش دوباره اجرایش نکند:

```js
window.history.replaceState({}, "", window.location.pathname);
```

### ۴.۳ `services/formValidation.js` — چرا اعتبارسنجی خودمان

مرورگر خودش `<input type="email" required>` را چک می‌کند، ولی پیامش یک **حباب
خاکستری سیستمی** است که هیچ ربطی به تم سایت ندارد و قابل استایل دادن نیست.

راه‌حل:

```jsx
<form noValidate onSubmit={handleSubmit}>
```

`noValidate` اعتبارسنجی مرورگر را خاموش می‌کند و خودمان پیام می‌دهیم.

> ⚠️ این فقط ظاهری است. **اعتبارسنجی واقعی همیشه سمت سرور است.** هر کسی می‌تواند
> جاوااسکریپت را دور بزند و مستقیم به API درخواست بزند. استرپی خودش دوباره چک
> می‌کند — و آن چکِ آخر است که اهمیت دارد.

### ۴.۴ `components/AuthSidebar.jsx`

پنل ورود. نکته‌هایش:

- **یک فرم، دو حالت.** `mode === "login"` تعیین می‌کند کدام فیلدها باشند
- **همه‌ی فیلدها به state وصل‌اند.** قبلاً `Name`، `Phone` و `Region` وصل نبودند و
  موقع ارسال **بی‌صدا دور ریخته می‌شدند**
- **هر سه provider در هر دو تب**، با فعل متفاوت: `Log in with` و `Sign up with`

### ۴.۵ `components/ForgotPasswordDialog.jsx` — دو مرحله

```
مرحله ۱: ایمیل  →  استرپی کد می‌فرستد
مرحله ۲: کد + رمز جدید  →  وارد می‌شود
```

**چرا رمز جدید هم می‌گیریم؟** تو گفتی «کد را بزند و وارد شود». ولی اندپوینت استرپی
رمز جدید لازم دارد، و منطقش درست است: اگر فقط با کد وارد شود، **رمز قدیمی همچنان
معتبر می‌ماند** و آن کد در ایمیلش باقی است.

**نکته‌ی امنیتی:** استرپی همیشه به `forgot-password` جواب موفق می‌دهد، حتی برای
ایمیلی که نمی‌شناسد. اگر فرق می‌گذاشت، هرکسی می‌توانست با امتحان کردن ایمیل‌ها
بفهمد **چه کسانی در سایت تو حساب دارند**.

**چرا فقط وقتی باز است mount می‌شود:**

```jsx
{isForgotOpen ? <ForgotPasswordDialog ... /> : null}
```

اول با `useEffect` پنج تا state را ریست می‌کردیم، که هم لینت گرفت هم شکننده بود.
وقتی کامپوننت هر بار **تازه ساخته شود**، حالت اولیه‌اش خودبه‌خود تمیز است.

### ۴.۶ `components/InlearnSelect.jsx` — چرا `<select>` بومی نه

**لیست بازشده‌ی `<select>` را نمی‌شود با CSS استایل داد.** آن کادر را سیستم‌عامل
می‌کشد، نه صفحه.

پس یک دکمه و یک لیست ساختیم — عناصر معمولی که استایل می‌پذیرند. ولی قیمتش این است
که رفتاری که `<select>` مجانی می‌داد باید دستی نوشته شود: فلش بالا/پایین، Enter،
Escape، کلیک بیرون، و نقش‌های `listbox`/`option` برای screen reader.

بالای ۱۲ گزینه یک جعبه‌ی جستجو هم اضافه می‌شود، و **تطابق‌های ابتدای کلمه اول
می‌آیند**: تایپ `ir` باید `Iran` را قبل از `Ireland` بیاورد، نه وسط لیست.

### ۵.۲ `src/middlewares/inlearn-profile-fields.js` — اولین کد بک‌اند

اندپوینت ثبت‌نام استرپی هر فیلد اضافه‌ای را رد می‌کند:

```
Invalid parameters: phone, region
```

**این سخت‌گیری عمدی و درست است.** بدون آن، یک غریبه می‌تواند موقع ساختن حساب خودش
`confirmed: true` یا `role: 1` بفرستد و به خودش دسترسی بدهد.

پس **در را برای همه‌چیز باز نکردیم** — فقط دو فیلد را با اسم نام بردیم:

```js
const PROFILE_FIELDS = ['phone', 'region'];

module.exports = (config, { strapi }) => {
  return async (ctx, next) => {
    // ۱. دو فیلد را از بدنه برمی‌داریم، قبل از اینکه اعتبارسنج ببیندش
    const lifted = {};
    for (const field of PROFILE_FIELDS) {
      if (typeof ctx.request.body[field] === 'string') {
        lifted[field] = ctx.request.body[field].trim();
      }
      delete ctx.request.body[field];
    }

    // ۲. می‌گذاریم استرپی کار خودش را بکند
    await next();

    // ۳. حالا کاربر ساخته شده — فیلدها را رویش می‌نویسیم
    const created = ctx.response.body?.user;
    await strapi.documents('plugin::users-permissions.user').update({
      documentId: created.documentId,
      data: lifted,
    });
  };
};
```

و در `config/middlewares.js` ثبتش می‌کنیم:

```js
'strapi::body',
'global::inlearn-profile-fields',   // بعد از body، قبل از روتر
```

**بعد از `strapi::body`** چون به بدنه‌ی پارس‌شده نیاز دارد. **قبل از روتر** چون
روتر همان جایی است که رد می‌کند.

**و اگر ذخیره شکست بخورد چه؟**

```js
} catch (error) {
  strapi.log.error('Could not save profile fields...');
  return;   // ثبت‌نام را خراب نمی‌کنیم
}
```

حساب در آن لحظه ساخته شده. تبدیل کردن یک ثبت‌نام موفق به خطایی که کاربر می‌بیند،
نتیجه‌ی بدتری است.

## خلاصه در یک جمله

**استرپی سیستم کاربری کامل را آماده می‌دهد؛ کار ما فقط این بود که به آن بگوییم چه
کسی اجازه‌ی چه کاری دارد، و دو فیلد اضافه را با اسم معرفی کنیم — بدون اینکه در را
برای هر چیز دیگری باز کنیم.**
